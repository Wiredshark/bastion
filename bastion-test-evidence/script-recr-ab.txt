note ITEM 11 RESTORE -- THE A/B. Sized by measurement, not by guess.
note
note ★ SIZING, FROM ITEM11-CALIBRATION-RESULTS.md (a run that already happened):
note   0.035 sim-seconds per client tick, stable across four intervals
note   (0.034-0.037), measured as (1.0 - recreation) / 0.0002 at five samples.
note
note   recreation decays 1.0 -> comfort 0.4 in (1.0-0.4)/0.0002 = 3000 SIM-s.
note   3000 / 0.035 = ~84,000 client ticks before the preempt CAN fire.
note   One break is RECREATION_BREAK_SECS = 120 sim-s = ~3,430 client ticks.
note
note ★★ THIS IS WHY THE CALIBRATION ARM EXISTED. A 5-minute run reaches ~600
note   sim-s -- one fifth of the way to the first break -- and would have read
note   EXACTLY like a restore that does not work. The number had to be measured
note   before this script could be written.
note
note ★★★ THE BAR IS NET-ACROSS-A-BREAK, NEVER PER-TICK. A restore that merely
note   SLOWED the decay would pass a "did recreation rise this tick" check and
note   leave the ratchet one-way. So the dense phase below samples every 1,000
note   ticks (~35 sim-s), which resolves a 3,430-tick break into ~3 samples:
note   one before, one inside, one after. Point sampling a TRANSITION is the
note   error item 13c already paid for; a 120-s break is not a transition, and
note   the cadence is stated here rather than assumed adequate.
note
note ★ RUN THIS WITH BOTH ARMS: 'recrab' (BASTION_RECREATION=1) and 'recrabctl'
note   (flag off, identical script). The control is the pre-existing behaviour:
note   recreation strictly NON-INCREASING for every colonist. If the control
note   ever rises, the A/B is void and the rise is the finding.
