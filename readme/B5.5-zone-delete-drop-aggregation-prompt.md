## Context
B5 works: paint → claim → walk → mine → stone drops. The live demo revealed: (1) designations/zones cannot be
deleted once painted; (2) a mined-out area is carpeted with individual item-drop entities (each a full ECS
entity with physics) — hundreds accumulate because hauling doesn't exist until B6. Even after B6, burst
mining will out-produce hauling, so aggregation is needed regardless.

## Part 1 — Zone/designation deletion
- Add an **erase verb** to the designation tools: paint-to-remove (same brush interaction as painting, but
  clears designations in the brushed cells) AND a **delete-entire-zone** action (select zone → remove).
- Deletion must **release cleanly**: any colonist-claimed jobs inside the erased area are cancelled via the
  existing B4 cancel machinery (proven: cancel releases within one cycle). No orphaned claims, no colonist
  stuck walking to a job that no longer exists (the watchdog covers stragglers, but cancel should beat it).
- Partial erase of a zone leaves the remainder intact and functioning.
- **Test:** paint a zone, let colonists claim, erase half mid-work → claims in the erased half released
  within one arbitration cycle, work continues in the remainder; delete the whole zone → all claims released,
  colonists return to idle/other work. Run alongside `--b4-scenario` and `--b5-scenario` (both must stay
  green).

## Part 2 — Item-drop aggregation (merge, NEVER delete)
**The invariant rules this design: colonist-produced items are player resources — item LOSS is a bug the
harness already asserts against. Do not add despawn timers for colonist-produced drops. Aggregate instead.**
- **Stack-merge:** when an item drop spawns (or periodically), nearby drops of the SAME item type within a
  small radius merge into a single **pile entity** carrying a count (`stone ×47`). One entity, one physics
  body, one render mesh regardless of count.
- **Conservation-exact:** merging preserves counts precisely — N merged drops of k items = one pile of N×k.
  Extend the harness's item-conservation assertion to cover merge (mine 27 blocks → total items across
  drops+piles == expected, always).
- **Pile visual:** a pile renders as a single small heap mesh (may scale/vary slightly by count-tier: a few
  stones / a heap / a big heap). Reuse an existing crate/heap-like object model if one fits; a simple
  generated heap is fine. Vastly cleaner than pebble-carpet.
- **Interaction-compatible:** anything that can pick up an item drop must handle piles (pickup takes from the
  pile's count; empty pile despawns). Keep the API such that **B6's hauling naturally hauls piles** (hauling
  a pile of 47 is one trip's decision logic — exact B6 semantics are B6's problem, but don't paint it into a
  corner: piles must be enumerable/claimable like drops).
- **Vanilla safety:** vanilla loose-loot behavior (mob drops, despawn timers on non-colonist loot) is
  UNCHANGED unless trivially compatible — gate the aggregation on colonist-produced drops (or `bastion`
  flag) if touching the general path risks vanilla regressions. Vanilla flagless boot must stay clean.
- **Performance check:** scenario that mines a large area (200+ blocks) → assert total drop/pile entity count
  stays under a sane bound (e.g. ≤ a few dozen piles, not hundreds of drops), tick time bounded.
- **(Cheap, optional if trivial) render-distance culling** for drops/piles at long range — client-side only,
  zero sim impact. Skip if not near-free; aggregation is the real fix.
